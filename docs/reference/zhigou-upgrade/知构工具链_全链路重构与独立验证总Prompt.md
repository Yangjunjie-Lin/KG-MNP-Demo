## 四、按研究内容建立主链路，不把四项研究机械串成四个步骤

研究内容一是整体框架，不是一个位于数据处理之前的“加工模块”。OMS 是统一语义控制层，不是只在第三个页面运行一次的脚本。

本轮用户可见主链路统一为五个大模块：

业务资料 → 数据接入与规则化 → 本体建模 → 本体服务与版本管理 → 任务规划与业务执行 → 反馈评估与演进。

反馈更新分两路返回：

- 任务方案、Prompt 和工具配置更新 → 任务规划/业务执行。
- 规则、知识与本体元数据更新 → 本体候选、校验审核、版本管理与 OMS。

工程映射：

| 主模块 | 研究依据 | 本轮展开程度 |
|---|---|---|
| 数据接入与规则化 | 研究内容二 | 单页输入、处理结果、质量和独立测试，不展开内部小步骤 |
| 本体建模 | 研究内容三 | 重点展开为附件 HTML 的五大流程 |
| 本体服务与版本管理 | 研究内容一的本体服务层、研究内容三末端 | 单页交付包、服务可用性、版本结果和独立测试 |
| 任务规划与业务执行 | 研究内容一的任务规划 Agent、行动执行 Agent | 单页任务、方案、动作与业务结果和独立测试 |
| 反馈评估与演进 | 研究内容四 | 单页执行反馈、优化前后、回归审核与更新结果和独立测试 |

必须写明一个边界拆分：PPT 的研究内容三末端叫“本体服务与版本发布”；附件 HTML 的第五步叫“语义编译与交付验收”。本体五步保留 HTML 名称，输出交付包；后续服务/版本模块承接包完成注册、发布审核、固定版本加载与服务验收。研究内容三的发布后准确率仍需覆盖这个承接环节，不能把发布职责删掉，也不能把建模第五步误称为已上线。

上面的串行主链用于首次构建和全链路展示。已有有效发布版本时，业务任务可以直接读取 OMS/对象服务执行，不必每次重新清洗和建模。规则化数据可供任务参数和已定义对象的受控更新使用，但不能把未确认候选直接写入正式业务对象库。

## 五、采用可组合模块，不拆出五套系统

优先复用现有 ApplicationService、资源 API、Python SDK、CLI、Worker、语义内核和领域包，采用模块化单体或等价的轻量架构，不为了“模块化”强制引入五个微服务或新的中间件集群。

建立清晰边界：接入/规则化、建模、服务/版本、执行、反馈演进；共享契约、工件、任务、权限、审计和评测能力。目录可调整，但以最小安全迁移为准。

每个模块必须有：

- 明确的输入契约与版本校验。
- 与 UI 无关的可调用核心操作。
- 持久化、可导入导出的输出工件。
- 独立执行与独立评测入口。
- 正常、异常和至少一个输入变化后的结果变化测试。
- 可替换的工具/模型/业务适配器及可识别的运行模式。

整链编排必须调用与独立测试相同的模块核心，不能为展示复制一套实现。模块之间通过工件和明确服务契约交接，不读彼此前端状态，不从临时目录猜文件，不依赖共享可变全局对象。

核心交接信息至少包含：项目、批次、run_id、模块、输入/输出工件引用、schema_version、内容摘要、依赖版本、规则/工具/模型版本、执行状态、验证报告与来源引用。优先扩展既有契约，避免制造第二套权威。

可增加统一的模块执行/评测适配层，使用户能从当前项目选择“使用上游输出”或“导入合法模块输入”，再单独运行。导入后仍执行摘要、版本、项目边界和权限校验，不能把文件里的 APPROVED 字符串当作有效审批。

独立模块测试可以启动自己的最小真实依赖，不要求先点击完整链路。其他模块输入可使用显式版本化测试工件；被测试的核心不能被 Mock 成固定输出。整链验收必须重新串起真实上游输出。

承接事实候选、结构、规则、证据和依赖版本。

交付至少覆盖结构、实例、约束、基线依赖、映射、来源、审核、校验、查询、测试和 manifest；名称以仓库已有格式为准。清单不循环记录自身摘要。

对下载出来的实际包重新校验摘要、解包边界、图内容、查询结果、证据和审核引用，不能只验证内存对象。禁止用 JavaScript join 代替正式 SPARQL 验证。

页面展示“确认建模结果 → 实际语义文件、答案对比和交付状态”，并将同一包交给服务/版本模块，继续服务接入。编译、交付、注册、发布和部署状态必须分开。

五步各有持久化输入/输出快照与 lineage；后一步继承前一步及必要的原始数据引用，不重新填写或替换成另一份演示数据。

## 八、其余模块：界面简洁，输入输出不能空心化

### A. 数据接入与规则化

依照 PPT 保留模态识别、解析规划/工具选择、执行、质量校验、标准化和数据源绑定，以及质量不合格回流重处理机制。内部执行，不拆成 UI 小步骤。

先打通现有真实文件上传和 API 接入，至少用实际表格与实际文本/文档完成一个可消费的规则化批次；已有可用能力继续接入。PDF、图像、音频、视频及 REST/Webhook/SFTP/消息队列/SDK 均建立清晰适配边界和覆盖清单，具备环境时运行真实样本，不把只有元数据的处理说成 OCR/ASR 成功。

输出记录、文本、类型化来源位置、质量报告和处理轨迹，直接符合本体模块契约。坐标可以是页码/版面、单元格、记录键、字符区间或时间段，随模态明确；不伪造统一页码。

页面只比较“接入资料 → 规则化内容”，展示真实转换、保留的依据及问题；独立评测比较字段识别结果、覆盖和实际耗时。

### B. 本体服务与版本管理

接收同一个已验证交付包，完成现有 Registry、发布候选、必要审核、发布、版本选择与读取服务接入。复用 OMS、对象读取服务、动作目录/动作服务和业务对象库，不再做第二套包管理。

OMS 提供固定版本的对象类型、属性、关系、约束及动作/函数元数据；对象服务读取具体对象、关系和证据；动作实现由受控注册表/适配器绑定，不能执行领域包中任意脚本。

在明确的本地测试环境完成真实注册、读取、查询和版本切换验证；本地发布记录不等于真实外部平台已部署。未配置的 GraphDB/政务接口不阻断其他本地能力，但必须单列外部验证状态。

页面比较“已交付包 → 当前可用的元数据、对象、动作与版本”；测试固定版本读取、证据回查、非法包拒绝、版本切换及回滚。

### C. 任务规划与业务执行

接收业务目标、固定本体版本、业务对象快照、可用动作和权限上下文。

任务规划 Agent 通过 OMS/对象服务获取对象关系与规则，生成可校验方案；行动执行 Agent 只调用动作服务中的已登记动作。不得直接连接任意数据库/底层业务接口绕过本体服务。

提供一个可持久化的本地业务执行器：实际创建/更新测试工单等业务记录，返回动作收据并重读状态验证效果；不是只返回 success=true。任务计划、动作版本、对象版本、幂等键和权限需要可追溯。

页面比较“任务与当前对象 → 计划、实际动作和业务状态变化”；独立测试正常执行、无权执行、非法参数、重复请求、超时及失败。不要为了本轮展示另扩建优化求解器研究。

### D. 反馈评估与演进

承接真实执行轨迹、业务结果及人工反馈，关联 PPT 要求的任务、数据、工具、规则、版本五要素。

内部完成问题分析、优化候选生成、回归验证、风险/人工审核、版本发布；失败候选回到优化环节，不能先改活动版本再补验证。

输出问题定位、候选变更、前后评测、审核记录和更新/未更新结果。至少证明一个更新实际改变下一轮任务采用的配置或规则，并能回滚。没有新任务结果的版本指针移动不算闭环。

Prompt/工具配置更新作用于执行模块；本体/规则更新重新进入建模校验和版本流程。禁止直接改生产规则、改测试答案或降低验收门以制造“自演进成功”。

页面比较“旧版本执行问题 → 候选改动与复测后结果”；正常无问题可明确返回“无需更新”，不强制生成补丁。

## 九、必须修复的跨模块运行问题

### 1. 后端版本失效传播

输入、规则、基线、映射、模型/工具配置或候选内容变化后，根据显式依赖将受影响的下游产物和审批标为 STALE，记录失效原因。不是只清空 React 状态。

处理运行中竞态：旧任务晚到时不能覆盖新会话结果，不能用旧审核冻结新数据。审批、重验和最终提交都检查依赖版本/摘要及预期头。

保留历史快照供只读追溯，不覆盖不可变发布版本。新的构建会话失效不代表删除旧发布版；旧版是否可被新任务选择由明确策略决定。

### 2. 会话到期与安全恢复

先复现报告中的 401，区分浏览器会话过期、权限撤销、后台任务权限和业务数据失效，不能混为一个 STALE。

会话到期应暂停新写请求并提示重新认证；认证恢复后按原 run_id/job_id 重新读取真实状态、提交收据与权限，再决定继续或重试。重复提交仍使用幂等保护。

不能靠关闭鉴权、永久会话、前端造审批身份或给所有用户管理员权限解决。不能在重新登录后无条件重放业务动作；403/权限撤销仍拒绝，未知外部副作用先核对后处置。

### 3. 门禁与状态

冻结运行前的必需检查清单。各检查分别记录 PASS、FAIL、NOT_RUN、ERROR、TIMEOUT、UNSUPPORTED 或有理由的 NOT_APPLICABLE，并标明 required。

required 检查未真实通过，禁止形成可构建/可交付/可发布的成功状态；不能跳过未配置检查后显示“全部通过”。AI 输出结构有效不等于语义正确，校验通过不等于人工审核完成。

### 4. 权限与执行隔离

延续现有项目隔离、CSRF/Origin、短期会话、授权下载、Worker 提交保护和审核角色策略。测试使用独立合成工作区与测试身份，不能拿测试审批证明真实专家审核。

不得把用户上传文本中的指令当作可执行权限；模型只提出候选/计划，工具白名单、参数 Schema、动作权限和运行策略独立执行。

## 十、真实模型、确定性运行与模拟结果分开记账

按实际实现区分：

- DETERMINISTIC：真实解析、映射、编译、校验、查询或规则执行。
- RECORDED：显式录制输出，用于可重复测试，不算实时模型推理。
- LIVE：实际模型服务/模型推理调用，有模型版本、输入摘要和请求收据。

另行记录数据是否合成、执行环境是否本地/外部。不要把“合成数据”“录制模型”“本地动作执行”混成一个真假开关。

优先完成确定性后端全链路，再在现有条件内接通并运行真实模型；不能因暂缺 GPU 只交一份审计文档，也不能因离线链路跑通宣称 AI 研究功能完成。

对已有 Qwen/vLLM、BGE-M3/FAISS、重排和修复适配，检查实际版本、配置、可用能力与 Schema。可使用明确记录的替代模型，但不能偷偷改方法或伪造相似度/模型调用。

缺模型、凭证或硬件时，交付可配置入口、实际尝试证据与 BLOCKED 原因；继续完成所有无依赖的工作。不得自行购买算力、申请付费服务或上传用户敏感资料。代码里不写死密钥。

研究中使用推理能力时，记录结构化决策、简短理由和证据引用即可，不要求输出或保存模型的隐藏思维链。

## 十一、每项研究都能单独做效果测试

提供统一评测入口及每项研究的独立套件，与业务 UI 运行共用核心实现。评测报告至少含数据版本/摘要、样本量、标注来源、标准答案、比较方法、分母、失败项、工具/模型版本、实际耗时和执行证据。

研究内容一的独立套件测试协同框架/服务边界：使用版本化输入工件组合真实服务，检查语义版本一致、对象读取、动作权限、任务到执行再到反馈的关联，以及更新/回滚的实际影响。它不是一个额外“第零加工步骤”。

研究内容二单独输入原始资料，测规则化结果和来源位置；不能要求用户先手动跑完本体。

研究内容三单独输入规则化工件、目标规则和可选本体，跑五步与语义验收；评估已发布内容时再调用服务/版本承接模块，不要求先跑完整外部采集链。

研究内容四单独输入版本化执行记录、反馈与候选配置，完成问题识别、候选优化和隔离环境的回归；运行反馈需有来源，不能用手写成功日志假冒上一轮执行。

PPT 的目标不得擅改：

| 研究内容 | PPT 目标 |
|---|---|
| 一 | 选取林业管理等典型任务，搭建完整原型并系统验证与评估；未规定统一数值阈值 |
| 二 | 项目名称、申请主体等关键字段识别准确率达到 85% 以上；准确率稳定前提下，单位数据平均处理时间较传统单一工具方案缩短 10% 以上 |
| 三 | 本体业务对象和属性关系识别准确率达到 80% 以上；专家审核后正式发布内容准确率达到 90% 以上；知识来源可追溯完整率达到 90% 以上 |
| 四 | 异常问题识别准确率达到 80% 以上；启用反馈演进后，典型业务任务完成率提升 10 个百分点以上 |

“项目名称、申请主体”等原指标保留；古树编号、巡查状态等作为额外领域指标单列，不能替换原指标后声称已完成原研究目标。

PPT 未定义的准确率口径、标注细则、样本量和统计方法属于待明确的工程评测协议：先写清并冻结，再计算。对象/属性/关系分项报告，必要时补充精确率、召回率和 F1，不能用有歧义的总百分比掩盖漏检。

时间改善按相同输入、相同硬件/缓存约定、可比正确性和失败口径计算；明确冷启动与稳态，不删掉失败样本美化速度。任务完成率提升用“之后完成率－之前完成率”的百分点差，不用相对百分比替代。

独立真值在模型构建/优化之前冻结；评测答案不能提供给生成/修复流程作弊。区分开发、回归与留出测试；没有真实专家审核不能报告专家审核后指标已达成。

微型合成样本只证明工程链路；不证明跨模态效果或研究目标达成。无标注、样本不足或缺正式运行时标 INSUFFICIENT_EVIDENCE/NOT_RUN，指标不达标时如实 FAIL，不能修改金标准或门限。

## 十二、必须实际跑的实例与变化测试

### A. 延续现有员工—部门回归

复用原本的员工/部门输入和构建前预期，确认 5 个对象、18 条业务三元组、21 个支持关联和三条精确答案。计数来自实际生成结果，不写死在界面或引擎里；新增表格行、修改名称、关系或规则后必须相应变化。

重点补齐真实确认建模包、最终 .kgop、授权下载、解包复验、下游导入和对象查询。另一领域 MNP 包成功不能替代 HR 包完成。

该场景放测试数据与普通批次加载入口，不恢复“案例教程”页面。测试角色审批只证明审核机制，不证明专家语义准确率。

### B. 新增一个林业闭环实例

以下是本轮拟定的合成工程测试数据，不是 PPT 提供的真实林业数据，也不是林业诊断规则：

- 3 株古树：GT-001、GT-002、GT-003，分别位于两个管护区域。
- 3 条带记录/原文来源的巡查：GT-001 明确“需要复查”；GT-002 明确“无需复查”；GT-003 “尚未完成检查，状态待核实”。
- 业务任务：为明确需要复查的对象创建复查工单，未知状态进入待核实列表；同一对象同一巡查不能重复建单。
- 构建前冻结预期：GT-001 创建一个工单；GT-002 不建单；GT-003 进入待核实列表，不能误判为无需复查或已异常。

用真实文件/数据启动规则化，经过本体五步、服务加载、任务规划、动作执行，再读取持久化工单状态与来源，最后形成反馈、一个受控更新及更新后的再执行验证。

这一路的对象数量按实际类/实例计算，不能套用 HR 的 5/18/21。核心 UI 和后端不得硬编码只识别 Employee/Department 或 Tree；领域差异进入 Domain Pack、映射、规则和动作注册。

### C. 必测异常与变化

至少覆盖：缺失必要来源、未知引用、重复身份、关系冲突、否定/未知状态、引文不匹配、无基线新建、输入变更后下游 STALE、运行中旧任务晚到、旧审批复用被拒、修复后重验重审、必需检查未运行、文件被篡改、权限不足、会话 401 恢复、重复动作幂等、反馈回归失败不生效、更新成功作用于下一轮以及回滚。

至少安排一次合法输入变化带来可解释输出变化，并证明与原输入相同则不会凭空增减结果。界面、下载产物、查询结果与持久化状态相互一致。

故障注入用于验证检测与恢复，不得把故意破坏的旧版本当作研究效果比较基线，制造虚假的“提升 10 个百分点”。

## 十三、测试执行、证据与最终判定

分层运行：模块核心/单元、模块契约与独立效果、跨模块集成、真实浏览器全链路、版本/安全回归，以及具备条件时的 LIVE 模型与多模态评测。

真实浏览器的主线测试不得 Mock 掉核心 API。实际启动后端和 Worker，用隔离项目加载批次；核对五步前后表格、关系图、审核暂停、401 恢复、工件下载和跨模块交接。单元测试可对外部网络边界使用明确替身。

运行既有后端、前端、静态检查、构建和完整测试收集；必要时分区执行，但最终所有分区必须对应同一代码快照，列出 passed/failed/skipped/error 与缺失分区，不只给选择集结果。

最终验证前冻结明确的代码提交/源码树摘要。测试后代码又变化，重跑受影响检查并重新标明证据适用范围；报告文件自身的生成不伪造成代码被测。对比旧失败和新失败，不通过删测试制造全绿。

至少保存五个本体阶段的真实前后截图、一次冲突修复、下游服务读取、业务对象状态变化、反馈更新前后、1366×768 专注模式，以及请求/任务/产物的关联记录。截图不出现密钥或真实敏感数据。

不要只给一个总 PASS。分别判定：

- 本体五步是否达到独立运行与汇报就绪。
- 四项研究是否各有可运行、可复现的独立测试。
- 选定本地配置的端到端链路与反馈闭环是否通过。
- 模型/多模态实际覆盖及各研究指标是否达成。
- 完整回归、安全与兼容是否通过。
- 本地品牌/代码迁移与 GitHub 原地更名是否分别完成。
- 是否具备正式发布资格；不得由以上部分结果自动推导。

可使用 ONTOLOGY_WORKBENCH_READY、LOCAL_CHAIN_PASS、MODULE_TESTS_READY 等有范围的结论。只有对应必需门真实通过才能标通过；LIVE 未运行、远端更名失败、研究效果不足等分别保留，不能被本地成功覆盖。

## 十四、实施顺序、清理与交付

按以下顺序执行，不要求用户逐条再发 Prompt：

保护本地增量并核对缺口 → 研究/模块/契约映射与安全命名迁移 → 修复状态和服务断点 → 打通本体五步真实产物 → 简化工作台并统一各模块界面 → 完成林业全链路与独立评测 → 运行修复/失效/401 等负向测试 → 同修订回归与文档 → 有权限时原地更名 GitHub 并复核。

清理旧教程路由、重复演示入口、旧品牌文案、无引用组件与临时构建文件。先列用途和替代去向；历史验收、领域包、测试证据、用户数据与兼容入口不能当作垃圾删除。旧教程 URL 可重定向到对应大阶段，但不保留第二套状态机。
